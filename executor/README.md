# خدمة تنفيذ الأكواد المحلية

هذا إعداد اختياري منفصل عن تشغيل الموقع واستيراد بياناته. فُعّلت الخدمة على جهاز التطوير الحالي بعد موافقة المالك يوم 5 نوفمبر 2026؛ لا يغيّر `npm run setup` إعدادات أي جهاز لتثبيتها تلقائيًا.

## حالة التشغيل المحلية الحالية

يعمل Docker Engine 29.9.3 داخل Ubuntu 24.04 WSL، وحاوية `ttwar-executor-local-piston-1` على 127.0.0.1:2000، مع cgroup v2. حزم Piston المثبتة توفر JavaScript 20.11.1 وPython 3.12.0 وJava 15.0.2 وC/C++ 10.2.0. هذه الإصدارات هي الحزم المتاحة من المصدر المستخدم؛ دعم إصدارات أحدث ونشر الخدمة للعموم يحتاجان مراجعة تشغيل مستقلة.

نجح اختبار جمع 2 و3 فعليًا في اللغات الخمس، ونجح التشغيل من واجهة المنصة. توقفت حلقة JavaScript غير المنتهية بمهلة نحو 3 ثوانٍ، وأعاد تجاوز المخرجات `output_limit`. أظهر فحص محدود للبرنامج loopback فقط وغياب مسار Windows `/mnt/c`؛ هذه فحوص وظيفية محددة وليست تدقيق أمان شاملًا للعزل.

ضُبط عنوان الخدمة في ملف البيئة المحلي فقط؛ هذا الملف وصورة Docker وحزم اللغات ليست ضمن ZIP. جهاز آخر يحتاج تجهيز الخدمة وإعداد ملف البيئة الخاص به. لا تُحفظ المحاولات أو النقاط لمجرد نجاح تشغيل البرنامج.

جلسة خلفية محلية تبقي Ubuntu WSL عاملًا أثناء الاستخدام الحالي. بعد إعادة تشغيل الجهاز، افتح Ubuntu WSL واترك الجلسة عاملة، ثم من مجلد المشروع شغّل:

```sh
sudo service docker start
sudo docker compose -f executor/compose.yaml --profile execution up -d
```

بعدها شغّل الموقع بالطريقة المعتادة، وافحص `npm run check:executor` من بيئة Node التي تشغّل API. ملف Compose لا يعيد تشغيل الحاوية تلقائيًا عند إقلاع المضيف؛ بدء الخدمة إجراء صريح. تعليمات التثبيت التالية مخصصة أيضًا لتجهيز جهاز جديد، وليست طلبًا لإعادة تثبيت المحرك الحالي.

## ما يحتاج مراجعة قبل التشغيل

ملف `compose.yaml` يتبع طريقة [Piston الرسمية](https://github.com/engineer-man/piston/blob/master/docker-compose.yaml): يحتاج حاوية `privileged` لكي تهيئ isolate وcgroup. تمنحها هذه الصلاحية وصولًا واسعًا داخل مضيف Docker أو آلة Linux الافتراضية؛ لا تعادل حاوية ذات صلاحيات محدودة. استخدم بيئة Linux مخصصة للتطوير وتجنب مشاركة المضيف مع بيانات حساسة أو خدمات إنتاج. لا يثبت هذا الملف وحده سلامة تنفيذ كود عدائي.

الإعداد يفتح `127.0.0.1:2000` فقط، ويستخدم volume خاصًا لحزم اللغات وtmpfs مؤقتًا، دون bind mount لكود المشروع أو ملفات البيئة أو Docker socket. ثُبتت الصورة الرسمية عند البصمة التي أعادها GHCR يوم 5 نوفمبر 2026: `sha256:2f66b7456189c4d713aa986d98eccd0b6ee16d26c7ec5f21b30e942756fd127a`. ثبات البصمة ليس تدقيقًا أمنيًا للصورة. توجد حدود عامة للحاوية والعمليات والتوازي، وتعطيل شبكة برامج المستخدم في إعداد Piston؛ تحقق عمليًا من تطبيقها لدى المضيف قبل أي نشر عام.

## متطلبات الجهاز

تحتاج Linux amd64 مع محرك Docker عامل وCompose وcgroup v2. [دليل Piston](https://github.com/engineer-man/piston/blob/master/readme.md) يوضح متطلبات المضيف وتثبيت اللغات؛ الخدمة لا تأتي بلغات مثبتة تلقائيًا. واجهته العامة تتطلب تصريحًا من المزوّد وليست بديلًا تلقائيًا لخدمة محلية.

قبل التفعيل على جهاز الفحص: كانت ملفات Docker Desktop 4.43.2 موجودة لكن لا يوجد محرك قابل للاتصال عبر Docker CLI. Ubuntu WSL يعمل بنواة 6.6.87.2 وcgroup2fs، ولم يوجد أمر Docker داخله حينها. تشغيل واجهة Docker Desktop في الخلفية لم يجعل المحرك متاحًا. لم تُغيّر إعدادات Windows أو العضويات يدويًا؛ تثبيت Docker Engine اللاحق داخل Ubuntu أضاف حزم النظام وخدمة Docker وشبكتها المعتادة بعد الموافقة.

أعاد أمر البدء الرسمي من إضافة Docker Desktop خطأ غياب مفتاح تسجيل Docker Desktop في Windows، لذلك لا تكفي الملفات الموجودة لتشغيله. لم يُنشأ مفتاح تسجيل يدوي ولم يُعد تثبيت Docker Desktop. البديل المقترح لتجاوز هذا العائق هو تثبيت المحرك داخل Ubuntu WSL بعد مراجعة تغييرات المضيف المطلوبة.

عند تجهيز جهاز جديد، يمكن إصلاح وتشغيل Docker Desktop من إعداداته المعتادة، أو تثبيت Docker Engine داخل Ubuntu WSL كما تم على الجهاز الحالي. للخيار الثاني يوجد سكربت مستقل قابل للمراجعة مبني على [تعليمات Docker الرسمية لـUbuntu](https://docs.docker.com/engine/install/ubuntu/):

```sh
# داخل Ubuntu WSL المقصود، من جذر المشروع، وبعد مراجعة تغييرات النظام:
sudo env TTWAR_INSTALL_DOCKER=1 bash executor/install-docker-ubuntu.sh
```

يثبت السكربت حزم Docker من مستودعه الرسمي ويبدأ المحرك داخل Ubuntu. يتوقف عند وجود حزم متعارضة أو ملفات إعداد سابقة، ولا يحذفها ولا يضيف مستخدمًا إلى مجموعة docker. بدون المتغير الصريح يخرج دون تغيير. يحتاج التنزيل مساحة واتصالًا، وقد يبدأ تثبيت الحزم خدمة النظام تلقائيًا. لا تثبت محركًا ثانيًا إذا كان لديك محرك قائم تريد الاحتفاظ باستخدامه. لا تنفّذ أوامر إعداد المضيف لمجرد نسخ المشروع.

## تشغيل Piston وتثبيت اللغات

بعد مراجعة صلاحية الحاوية وتوفير محرك عامل، نفّذ من جذر المشروع داخل مضيف Docker المقصود:

```sh
docker compose -f executor/compose.yaml --profile execution config --quiet
docker compose -f executor/compose.yaml --profile execution up -d
```

تحقق من `http://127.0.0.1:2000/api/v2/runtimes`. إذا كانت القائمة فارغة فالاتصال قائم لكن اللغات غير مثبتة. استخدم مدير حزم Piston الرسمي، أو `GET /api/v2/packages` لمعرفة الحزم المتاحة ثم `POST /api/v2/packages` بحقلَي `language` و`version` لتثبيت النسخ المطلوبة. مثال طلب تثبيت Python: `{"language":"python","version":"*"}`. تحقق من الأسماء الفعلية في قائمة الحزم؛ هدف المحرر JavaScript وPython وJava وC وC++. قد يوفر اسم حزمة واحد أكثر من لغة تنفيذ. لا يتضمن هذا المشروع مدير حزم يثبتها تلقائيًا، ولا يرسل طلبات تثبيت من الواجهة العامة.

بعد توفير اللغات، اضبط في `backend/.env` لبيئة التطوير فقط:

```dotenv
CODE_EXECUTOR_URL=http://127.0.0.1:2000/api/v2/execute
```

إذا كان API نفسه داخل حاوية، فـ127.0.0.1 يشير إلى حاويته. هذا الإعداد مخصص لـAPI الذي يعمل على الجهاز، وليس شبكة Docker Compose الإنتاجية. البيئة الإنتاجية تتطلب HTTPS وعزلًا ومراجعة تشغيل مستقلة. `CODE_EXECUTOR_TOKEN` اختياري لخدمة المالك؛ Piston المحلي الخام لا يضيف مصادقة تلقائية، لذلك لا تفتح منفذه على الشبكة.

## فحص الجاهزية والتشغيل التجريبي

تعرض واجهة المحرر الآن نتيجة فحص حي للغات: `ready` للخمس، و`partial` لبعضها، وحالات منفصلة لانقطاع الاتصال والرد المشوه وغياب اللغات أو الإعداد. وقت الفحص ظاهر، والمسودات تظل قابلة للتعديل والتنزيل للغات غير المثبتة. قراءة status عامة ولا تنفذ كودًا؛ تخزن النتيجة خمس ثوانٍ، وتشارك الطلبات المتزامنة، بمهلة ثلاث ثوانٍ وحد رد 128 KiB. يستخدم الفحص مسار `/runtimes` الشقيق لـ`/execute` من نفس الأصل دون تحويلات أو query أو hash، ويرسل رمز المالك الاختياري فقط. يفحص كل طلب تشغيل مصادق عليه اللغات مجددًا قبل إرسال الكود، ويرفض الخدمة أو اللغة غير المتاحة بـ503. لا إعادة إرسال تلقائية ولا تبديل للغة المسودة. الفحص لقطة للتوفر ولا يثبت سلامة العزل أو نجاح تشغيل لاحق. يبقى أمر التشخيص أدناه أشد في معنى الجاهزية: يحتاج اللغات الخمس كلها ليخرج بصفر، بينما يسمح المحرر بالتشغيل بلغة مثبتة ضمن الحالة الجزئية.

```sh
npm run check:executor
npm run check:executor -- --smoke
```

الأمر الأول يقرأ `/runtimes` فقط: لا يشغّل كودًا أو يثبت لغة. يميّز غياب الإعداد وفشل الاتصال والرد المشوه ونقص اللغات الخمس. لا يطبع URL الكامل أو query أو رمز المالك، ولا يتبع تحويلات. رمز الخروج صفر عند الجاهزية، و2 إذا احتاج إعدادًا، و1 عند خطأ استخدام الأمر. يحتاج مسار Piston قياسيًا ينتهي بـ`/execute` كي يحدد مسار `/runtimes` الشقيق؛ لا يخمّن مسارات الخدمات المخصصة.

`--smoke` الصريح يرسل خمسة برامج ثابتة لجمع 2 و3 إلى الخدمة المضبوطة، بعد اكتشاف اللغات كلها، ويتحقق أن stdout هو 5. لا يقرأ أكواد المستخدمين أو ملف الحساب ولا يرسل JWT أو يحفظ محاولات أو نقاطًا. هذا اختبار توافق وظيفي؛ ليس اختبار اختراق أو إثباتًا لحدود العزل. قد يستغرق كل اتصال تنفيذ حتى المهلة المضبوطة، ولا توجد إعادة إرسال تلقائية.

بعد نجاح الفحص واختبار العزل، أعد تشغيل API ليقرأ متغيرات البيئة. لا تجعل زر التشغيل متاحًا بوضع عنوان وهمي؛ الحالة العامة الحالية تعني وجود إعداد صالح شكليًا، وليست فحصًا حيًا لاتصال الخدمة.

لإيقاف الخدمة مع الحفاظ على حزم اللغات:

```sh
docker compose -f executor/compose.yaml --profile execution down
```

لا تستخدم حذف volumes إذا كنت تريد الاحتفاظ باللغات المثبتة. لا يغير هذا الملف بيانات MongoDB أو ملفات JSON المستوردة.
